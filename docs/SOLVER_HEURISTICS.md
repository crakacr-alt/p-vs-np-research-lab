# Эвристика поиска solver-а

SAT solver остаётся точным: эвристика не решает, какой ответ правильный. Она
решает только, **какую ветку проверить первой**.

## Почему простой счётчик не всегда хорош

Старая версия выбирала переменную, которая встречается чаще всего.

Но одно вхождение в короткой клаузе может быть важнее нескольких в длинных.
Например, клауза из двух литералов ограничивает выбор сильнее, чем клауза из
пяти.

## Jeroslow–Wang

Для литерала в клаузе длины `k` добавляется вес:

```text
2^(-k)
```

Поэтому короткие клаузы получают больший приоритет.

Отдельно считаются positive/negative scores. После выбора переменной solver
сначала пробует полярность с большим score.

Для XOR-ограничения нет естественной полярности, поэтому его вес делится
поровну между True и False.

## Почему это безопасно

Если первая ветка не подходит, exact solver всё равно проверит вторую.
Следовательно, эвристика может изменить:

- число decisions;
- число recursive calls;
- время;
- глубину поиска.

Но она не должна изменить SAT/UNSAT ответ.

Именно поэтому после изменения прогоняются brute-force/differential tests.

## Decomposition

Независимые CNF-компоненты теперь находятся union-find алгоритмом.

Для каждой переменной мы запоминаем первую клаузу с этой переменной и объединяем
с ней следующие клаузы. Не нужно каждый раз обходить полный список всех
соседних клауз одной популярной переменной.

## Контрольное измерение

На 60 фиксированных random 3-SAT задачах:

```text
variables = 28
clauses   = 118
seeds     = 1..60
```

Hybrid/Switch:

```text
decisions: 727 -> 548
calls:     8006 -> 5529
```

45 случаев потребовали меньше decisions, 9 — больше, 6 не изменились.

Это эксперимент на конкретной выборке, а не доказательство превосходства
эвристики на всех SAT-задачах.
