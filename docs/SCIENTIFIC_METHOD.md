# Научный метод проекта

## 1. Сначала формулировка

Гипотеза должна быть проверяемой.

Плохо:

> hybrid solver лучше.

Лучше:

> На формулах, состоящих из независимых компонент, decomposition уменьшает число DPLL decisions относительно baseline при одинаковых входах.

## 2. Контроль

Для каждого улучшения нужен baseline.

В v0.2 baseline — простой DPLL.

## 3. Одинаковые входы

Если сравниваются два solver-а, они должны получать одну и ту же формулу с одним и тем же seed.

## 4. Повторяемость

Каждый эксперимент фиксирует:

- n;
- число клауз;
- ratio;
- seed;
- repeats;
- версию solver-а;
- метрики.

## 5. Сырые данные сохраняются

Нельзя оставлять только красивый итоговый график. CSV нужен для повторной проверки.

## 6. Время — не единственная метрика

Измеряются:

- decisions;
- recursive calls;
- propagations;
- cache hits;
- decompositions;
- max depth;
- wall-clock time.

Логические счётчики обычно воспроизводимее времени.

## 7. Отрицательный результат — тоже результат

Если гипотеза не выдержала тест, её статус должен стать \`COUNTEREXAMPLE_FOUND\` или \`REJECTED\`.

Удалять неудачные идеи из истории нельзя: иначе исследование будет циклически повторять старые ошибки.

## 8. Empirical fit != proof

Если по 20 точкам лучше подходит \`n^3\`, это не доказывает polynomial worst-case.

Если лучше подходит \`1.1^n\`, это также не доказывает строгую нижнюю границу.

Это только направление для дальнейшей математики.

## 9. SAT и UNSAT требуют разной осторожности

SAT легко независимо проверить найденной моделью.

UNSAT сложнее: отсутствие решения желательно подтверждать вторым независимым solver-ом или формальным proof certificate, когда такой модуль будет добавлен.

## 10. AI не является доказателем

LLM может:

- придумать гипотезу;
- написать эксперимент;
- искать объяснение;
- выбрать следующий тест.

Но статус \`PROOF_CANDIDATE\` должен означать только «есть формальный текст/артефакт, который надо независимо проверять».
